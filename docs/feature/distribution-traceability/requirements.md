## 背景与目标

现有平台可对单张图片嵌入并验证 Go DCT v1 短文本，密钥仅由单个环境变量提供，没有持久水印记录。下一阶段让管理员根据接收人名单生成不同副本，之后由已验证的水印标识查到副本登记信息，并在更换密钥后继续处理旧副本。

本轮范围按上一条建议解释为上述三个模块；扩展清单中的几何恢复、拍屏识别、SSO、外部发送、SDK 等没有被视为自动纳入。用户确认本快照，接受此范围解释。

## 用户场景

1. 管理员上传一张图片，填写/导入接收人名单，校验后生成每人不同的水印副本并打包下载。失败时知道失败原因，可修正后重试。
2. 管理员上传收到的图片，平台验证并提取标识，若存在本平台记录，则显示该副本登记接收人、批次、时间和密钥版本；没有记录或验证失败时明确说明。
3. 管理员创建新的密钥版本并切换用于新副本；旧密钥可保留为“仅提取”，使既有副本继续可识别。密钥停用的后果可见。
4. 重启服务后，批次/副本记录和密钥版本仍可用；持久状态不可读时显式报错，不能静默丢弃或初始化空库后假装成功。

## 失败与恢复规则

- 图片处理或记录持久化失败时不交付被标记为完整成功的批次；错误可定位到预校验、处理或保存阶段。
- 进程中断后在途批次状态必须能准确恢复或标为失败，不能永久显示虚假的处理中。
- 持久存储不可用、备份恢复不完整、旧密钥缺失均明确诊断，不能通过丢弃旧状态“修好”。
- 更换/停用密钥不会抹除用户已下载的副本；删除记录或缺少记录也不等于图中没有水印。
- 单张图提取成功只能证明该载荷通过指定算法与密钥的验证，不能单独证明登记接收人实际泄露。
